1.Overall Architecture

What DayFlow is a personal life-management app split into two independently-run projects that live in the same Git repository:
  • src/ — a Next.js 16 (App Router) frontend, running on port 9002.
  • backend/ — a standalone NestJS API server, running on port 3001, talking to MongoDB Atlas through Mongoose.

They are two separate Node.js processes with two separate package.json files and two separate tsconfig.json files. The frontend never talks to MongoDB directly — every piece of data goes through the NestJS backend's REST API.

Why this shape The project originally used Firebase (Firebase Auth + Firestore + Firebase Storage + Firebase Admin) directly from the Next.js app, including a handful of Next.js API routes that used firebase-admin on the server side. Over the course of this project the entire data and auth layer was migrated to a self-hosted NestJS + MongoDB backend, so the app is no longer dependent on any Firebase product.

Why NestJS specifically

NestJS is a Node.js framework built on top of Express that enforces a consistent, modular structure (Controllers, Services, Modules, DTOs, Guards). This repository leans on that structure heavily: every feature (tasks, expenses, habits, ...) is implemented as its own NestJS module with the same shape, which is what makes the codebase predictable once you understand one module.

Authentication model at a glance

DayFlow uses stateless JWT access tokens for authorizing API calls, plus a stateful refresh token stored as an httpOnly cookie and tracked in MongoDB, so a session can be revoked (logout, password reset) even though JWTs themselves cannot be "un-signed". This is explained fully in Sections 7–9.

Migration strategy

The migration was done incrementally and verified at each step, not as one big rewrite:

  1. Auth first — because every other feature depends on having an authenticated user id available.
  2. One feature at a time — Notes, Credentials, Notifications/Push/Settings, Expenses, Habits, Planner, then the Dashboard widgets that reuse those same features, then Profile.
  3. Verification by curl — every new/changed endpoint was exercised directly with curl against the running backend (register a throwaway user, call the endpoint, inspect the JSON, delete the test data) before wiring the frontend to it.
  4. Full Firebase removal last — once every feature had a working backend equivalent, all Firebase SDK code, config files, and npm packages were deleted in one pass (Section 21).
Where The single biggest structural difference: Firestore's old shape stored one document per collection per user, e.g. users/{uid}/data/todos holding { items: [...] }. MongoDB instead stores one document per item (e.g. one document per task) inside a shared tasks collection, with every document carrying its own userId field. This is why almost every list in the app now uses a real MongoDB _id as its identifier instead of a client-generated string id.

5.Controllers, Services, DTOs and Schemas

Every feature module follows the exact same four-part pattern. Here is the complete, real implementation of the Tasks feature (backend/src/modules/tasks/tasks.module.ts), annotated part by part:

1. Schema — what gets stored in MongoDB

@Schema({ timestamps: true, collection: 'tasks' })
class Task {
  @Prop({ type: Types.ObjectId, ref: 'User', required: true, index: true })
  userId!: Types.ObjectId;

  @Prop({ required: true, trim: true, maxlength: 500 })
  text!: string;

  @Prop({ default: false })
  completed!: boolean;

  @Prop({ enum: ['high', 'medium', 'low'] })
  priority?: string;
}
const TaskSchema = SchemaFactory.createForClass(Task);
What A Mongoose schema, declared with NestJS's decorator syntax (@Schema/@Prop) instead of a plain Mongoose new Schema({...}) call. It describes the shape, types, and constraints of a document in the tasks collection.

2. DTO — what a request body must look like

class TaskDto {
  @IsString() @MaxLength(500) text!: string;
  @IsOptional() @IsBoolean() completed?: boolean;
  @IsOptional() @IsIn(['high', 'medium', 'low']) priority?: string;
}
What A plain class decorated with class-validator decorators. NestJS's global ValidationPipe (Section 14) uses this class to validate every incoming request body before it reaches the controller method.

3. Service — the actual database logic

@Injectable()
class TasksService {
  constructor(@InjectModel(Task.name) private readonly model: Model<Task>) {}

  findAll(userId: string) {
    return this.model.find({ userId }).sort({ createdAt: -1 }).lean().exec();
  }
  create(userId: string, dto: TaskDto) {
    return this.model.create({ ...dto, userId });
  }
  update(userId: string, id: string, dto: TaskDto) {
    return this.model.findOneAndUpdate({ _id: id, userId }, dto, { new: true, runValidators: true }).exec();
  }
  remove(userId: string, id: string) {
    return this.model.deleteOne({ _id: id, userId }).exec();
  }
}
Why every query includes userId This is the ownership/authorization mechanism for the whole app (see Section 11). A user can never read, update, or delete another user's task, because the query itself only ever matches documents whose userId equals the id taken from their own verified JWT.

4. Controller — the HTTP routes

@Controller('tasks')
@UseGuards(JwtAuthGuard)
class TasksController {
  constructor(private readonly service: TasksService) {}

  @Get()    all(@CurrentUser() user: { sub: string }) { return this.service.findAll(user.sub); }
  @Post()   create(@CurrentUser() user, @Body() dto: TaskDto) { return this.service.create(user.sub, dto); }
  @Patch(':id') update(@CurrentUser() user, @Param('id') id: string, @Body() dto: TaskDto) { return this.service.update(user.sub, id, dto); }
  @Delete(':id') remove(@CurrentUser() user, @Param('id') id: string) { return this.service.remove(user.sub, id); }
}
Where @UseGuards(JwtAuthGuard) on the whole controller means every route in it requires a valid JWT (Section 7). @CurrentUser() is a custom parameter decorator (common/decorators/current-user.decorator.ts) that pulls the decoded JWT payload off the request object — it is never something the client can set directly.

Module registration

@Module({
  imports: [MongooseModule.forFeature([{ name: Task.name, schema: TaskSchema }])],
  controllers: [TasksController],
  providers: [TasksService],
})
export class TasksModule {}

Every other feature module (Expenses, Habits, Planner, Notes, Credentials, Notifications, Push) is built from the exact same four pieces, just with a different schema/DTO shape. The only structural variations worth knowing:

  • Expenses and Habits each declare two schemas in one file (Transaction+Budget, Habit+GymSettings) because those two pieces of data are logically related.
  • Habits' PATCH /habits and Planner's PUT /planner are replace-all operations, not per-item updates — see Section 17 for why this matters.

7.JWT Authentication

What JWT (JSON Web Token) is a signed, self-contained string that encodes a small payload (here: { sub: userId, email }) plus an expiry time. Because it is cryptographically signed with a server-only secret, the server can trust its contents without needing to look anything up — that is what "stateless" authentication means.

How the pieces fit together

PieceFileRole
JwtModule.registerAsync(...)modules/auth/auth.module.tsRegisters @nestjs/jwt's JwtService (used to sign/verify tokens). Registered with empty default options because each individual sign call supplies its own secret and expiry.
JwtStrategymodules/auth/strategies/jwt.strategy.tsA Passport.js strategy that extracts the token from the Authorization: Bearer <token> header and verifies its signature against JWT_SECRET.
JwtAuthGuardcommon/guards/jwt-auth.guard.tsA one-line NestJS Guard (extends AuthGuard('jwt')) applied to controllers with @UseGuards(JwtAuthGuard) to require a valid token.
CurrentUser decoratorcommon/decorators/current-user.decorator.tsPulls the verified payload (request.user, set by Passport after the guard succeeds) into a controller method's parameter.

The actual JwtStrategy code

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor(config: ConfigService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      secretOrKey: config.getOrThrow<string>('JWT_SECRET'),
    });
  }
  validate(payload: { sub: string; email?: string }) {
    return payload; // becomes request.user
  }
}
How authorization actually happens on every request
  1. Client sends Authorization: Bearer <accessToken>.
  2. JwtAuthGuard triggers Passport, which runs JwtStrategy.
  3. Passport verifies the signature and expiry using JWT_SECRET. If invalid/expired, the request is rejected with 401 Unauthorized before it ever reaches the controller.
  4. If valid, validate() returns the payload, which Passport attaches as request.user.
  5. The controller reads it via @CurrentUser(), e.g. user.sub is the MongoDB user id.

8.Access Token + Refresh Token Flow

What and why two tokens A single long-lived token would be dangerous to keep in browser JavaScript (if stolen via XSS, an attacker has access for a long time). DayFlow instead uses a short-lived access token (15 minutes, kept only in a JS variable, never persisted to localStorage) for calling the API, and a long-lived refresh token (30 days, stored as an httpOnly cookie so client-side JavaScript can never read it) used only to mint new access tokens.

Issuing tokens

Where AuthService.issueTokens(), backend/src/modules/auth/auth.service.ts
private async issueTokens(userId: string, email?: string) {
  const payload = { sub: userId, email };
  const accessToken = await this.jwt.signAsync(payload, {
    secret: JWT_SECRET, expiresIn: JWT_ACCESS_EXPIRES_IN, // default 15m
  });
  const refreshToken = await this.jwt.signAsync(payload, {
    secret: JWT_REFRESH_SECRET, expiresIn: JWT_REFRESH_EXPIRES_IN, // default 30d
  });
  await this.sessions.create({ userId, tokenHash: sha256(refreshToken), expiresAt });
  return { accessToken, refreshToken };
}

Note the two tokens are signed with two different secrets (JWT_SECRET vs JWT_REFRESH_SECRET), so a leaked access token can never be used to mint new tokens.

Where each token lives

Where AuthController, backend/src/modules/auth/auth.controller.ts
private setRefreshCookie(res: Response, token: string) {
  res.cookie('refresh_token', token, {
    httpOnly: true,       // JavaScript cannot read this cookie at all
    secure: true,
    sameSite: 'none',     // needed because frontend (9002) and backend (3001) are different origins
    path: '/api/auth',    // only ever sent to /api/auth/* routes, nowhere else
    maxAge: 30 days,
  });
}

Every auth endpoint (register, login, guest, refresh) calls this and returns only { accessToken } in the JSON body — the refresh token is never present in any response body or visible to frontend JavaScript.

The refresh_sessions collection (why refresh tokens can be revoked)

Where backend/src/modules/auth/schemas/refresh-session.schema.ts
@Schema({ timestamps: true, collection: 'refresh_sessions' })
export class RefreshSession {
  userId: Types.ObjectId;
  tokenHash: string;        // SHA-256 hash of the token — the raw token is never stored
  expiresAt: Date;          // TTL index: MongoDB auto-deletes the row after this
  revokedAt?: Date;         // set on logout, refresh, or password reset
}
How refresh + rotation works
  1. Client's access token expires; the next API call gets 401.
  2. Frontend calls POST /api/auth/refresh (no body needed — the httpOnly cookie is sent automatically by the browser).
  3. AuthService.refresh() verifies the refresh JWT's signature, then looks up its hash in refresh_sessions, checking it exists, is not revoked, and has not expired.
  4. If valid: that session row is marked revokedAt (so it can never be used again — this is refresh token rotation), and a brand new access+refresh pair is issued and stored.
  5. If invalid: 401 Unauthorized, and the frontend treats the user as logged out.

How the frontend uses this automatically

Where apiFetch(), src/lib/api-client.ts
export async function apiFetch<T>(path, init, retry = true) {
  const res = await fetch(url, { ...init, credentials: 'include', headers: { Authorization: `Bearer ${accessToken}`, ... } });
  if (res.status === 401 && retry) {
    const refreshed = await refreshSession();       // POST /auth/refresh
    if (refreshed) return apiFetch(path, init, false); // retry the original call ONCE
  }
  if (!res.ok) await parseError(res);
  return res.json();
}

This means every page in the app can just call apiFetch('/tasks') without ever thinking about token expiry — a mid-session expiry is invisible to the rest of the UI.

Logout and password reset also revoke sessions

logout() revokes the one session tied to the cookie being cleared. resetPassword() goes further and revokes all of that user's refresh sessions with sessions.updateMany({userId}, {revokedAt}) — so resetting a password immediately signs the user out everywhere (Section 10 & 16).

9.Password Hashing

What Passwords are never stored in a form that could be read back. They are hashed with bcrypt (via the bcrypt npm package), a slow, salted, one-way hashing algorithm purpose-built for passwords.
Why bcrypt, and why cost factor 12 Bcrypt is deliberately slow (tunable via a "cost factor") to make brute-force guessing of leaked hashes impractical. Cost factor 12 (used throughout this codebase) is a widely-recommended default that takes roughly 200–300ms per hash on typical hardware — fast enough for a real login, slow enough to make guessing millions of passwords expensive.

Where hashing happens

OperationFile / methodCode

The passwordHash field is hidden by default

Where backend/src/modules/users/schemas/user.schema.ts
@Prop({ select: false })
passwordHash?: string;

Because of select: false, a normal User.findById(...) query will never return the hash — not even by accident. Anywhere the backend actually needs to compare a password, it explicitly opts in with .select('+passwordHash') (see UsersService.findByEmail and findByIdWithPassword). This means an accidental typo like returning a raw user document from an API response could never leak a password hash.

The token schema

@Schema({ timestamps: true, collection: 'password_reset_tokens' })
export class PasswordResetToken {
  userId: Types.ObjectId;
  tokenHash: string;     // SHA-256 hash — raw token is never stored
  expiresAt: Date;       // TTL index — auto-deleted by MongoDB after 30 minutes
  usedAt?: Date;         // set the moment the token is used, enforcing single-use
}

Requesting a reset

async requestPasswordReset(email: string) {
  const user = await this.users.findByEmail(email);
  if (user?.email) {
    const rawToken = randomBytes(32).toString('hex');        // 256-bit random token
    await this.resetTokens.create({ userId: user._id, tokenHash: sha256(rawToken), expiresAt: now + 30min });
    const resetLink = `${FRONTEND_URL}/reset-password?token=${rawToken}`;
    await this.mail.sendPasswordResetEmail(user.email, resetLink);
  }
  return { success: true };   // ALWAYS success, whether or not the email exists
}
Why it always returns success If the endpoint returned a different response for "email not found" versus "email sent", an attacker could use it to check which email addresses have accounts on DayFlow (email/account enumeration). Returning an identical {success:true} either way closes that off. The frontend's copy reflects this too: "If an account exists for that email, we've sent a link..."

Completing a reset

async resetPassword(token: string, newPassword: string) {
  const resetToken = await this.resetTokens.findOne({
    tokenHash: sha256(token), usedAt: { $exists: false }, expiresAt: { $gt: new Date() },
  });
  if (!resetToken) throw new UnauthorizedException('Invalid or expired reset link');
  resetToken.usedAt = new Date();                    // single-use enforced here
  await resetToken.save();
  await this.users.updatePasswordHash(resetToken.userId, bcrypt.hash(newPassword, 12));
  await this.sessions.updateMany({ userId: resetToken.userId }, { revokedAt: new Date() }); // sign out everywhere
}

Sending the email — Resend

What is Resend Resend is a transactional email API. mail.service.ts wraps it in one method, sendPasswordResetEmail(to, resetLink). 
constructor(private readonly config: ConfigService) {
  const apiKey = config.get('RESEND_API_KEY');
  this.fromAddress = config.get('MAIL_FROM_ADDRESS', 'DayFlow <onboarding@resend.dev>');
  this.client = apiKey ? new Resend(apiKey) : null;
  if (!this.client) console.warn('RESEND_API_KEY is not configured. Password reset emails will not be sent.');
}
Graceful degradation If RESEND_API_KEY is not set, the app still works end-to-end — it just silently skips the actual send (with a console warning) instead of crashing. This matches the same pattern used for VAPID/push keys (Section 15).
Important operational limitation Resend accounts without a verified sending domain run in "sandbox mode": the from address must be Resend's own onboarding@resend.dev (you cannot send from a domain you don't own, like a personal Gmail address), and email can currently only be delivered to the developer's own verified Resend account address, not to arbitrary users. This was discovered and fixed during testing — see Section 17. Real end users will not be able to receive reset emails until a custom domain is verified on the Resend account.

11.User Authentication and Ownership / Authorization

Authentication vs. Authorization Authentication answers "who is making this request?" — handled entirely by JwtAuthGuard + JwtStrategy (Section 7). Authorization answers "is this user allowed to touch this specific piece of data?" — handled by every service method filtering its MongoDB query by that user's id.

The rule, applied everywhere

Every single feature query in the backend takes exactly this shape:

this.model.find({ userId })                                 // list
this.model.create({ ...dto, userId })                        // create
this.model.findOneAndUpdate({ _id: id, userId }, dto)         // update
this.model.deleteOne({ _id: id, userId })                     // delete

userId here always comes from @CurrentUser() → user.sub → the verified JWT payload. It is never taken from the request body, a URL parameter, or any other client-controlled input. This is what makes it impossible for User A to read, edit, or delete User B's data, even if they know the exact MongoDB _id of User B's document: the findOneAndUpdate/deleteOne filters on both _id and userId, so a mismatched owner simply matches zero documents.

Guest accounts

POST /api/auth/guest creates a real MongoDB user document ({username: 'Guest User', isAnonymous: true}, no email, no password) and issues a normal JWT for it. From the rest of the backend's point of view, a guest is authenticated exactly like any other user — the only special-casing is isAnonymous being used by the frontend to hide account-security UI (email/password change) that doesn't apply to a passwordless account.

Anonymous data isolation via sparse email index

@Prop({ unique: true, lowercase: true, trim: true, sparse: true })
email?: string;

sparse: true means the unique index only applies to documents that have an email field at all — so MongoDB allows unlimited guest users with no email, while still enforcing that every registered (non-guest) email is unique.

13.Frontend → api-client → NestJS → MongoDB Request Flow

Where src/lib/api-client.ts is the single file every page/hook goes through to talk to the backend.

The building blocks of api-client.ts

ExportRole
API_BASE_URLRead from NEXT_PUBLIC_BACKEND_URL (defaults to http://localhost:3001/api)
module-level accessToken variableHeld only in memory (not localStorage) — cleared on full page reload, restored via refreshSession()

A typical call, start to finish

// in a page component, e.g. src/app/dashboard/page.tsx
const created = await apiFetch<ApiTask>('/tasks', {
  method: 'POST',
  body: JSON.stringify({ text, completed: false, priority }),
});
  1. apiFetch builds the full URL (API_BASE_URL + '/tasks'), attaches Content-Type: application/json (because a body is present), Authorization: Bearer <accessToken>, and credentials: 'include' (so the httpOnly refresh cookie travels with the request even though this call doesn't need it directly).
  2. The browser sends the request cross-origin (frontend on :9002, backend on :3001).
  3. NestJS's CORS middleware (configured in main.ts with origin: FRONTEND_URL, credentials: true) allows it.
  4. Global body parser, cookie parser, ValidationPipe run (Section 14).
  5. JwtAuthGuard verifies the token; TasksController.create runs; TasksService.create inserts into MongoDB.
  6. The created document (with its new _id, createdAt, updatedAt) comes back as JSON.
  7. apiFetch checks res.ok; if not ok, throws ApiError. If ok, returns res.json() to the caller.
  8. The page maps the raw {_id, ...} shape into the frontend's own TodoItem type (_id → id) and updates React state.

See Section 20 for the fully worked version of this exact example, including the 401/refresh path.

14.Validation and Error Handling

Request validation — the global ValidationPipe

Where backend/src/main.ts
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,             // strip any property not declared on the DTO
  transform: true,             // convert plain JSON into an instance of the DTO class
  forbidNonWhitelisted: true,  // REJECT (400) requests that include undeclared properties
}));
Why forbidNonWhitelisted matters This makes every DTO an explicit allow-list. If a client sends a field the DTO doesn't declare (e.g. trying to sneak a userId into a task-creation body), the whole request is rejected with 400 Bad Request instead of the extra field being silently ignored or, worse, accidentally used.

class-validator decorators used across DTOs

DecoratorMeaning
@IsString(), @IsBoolean(), @IsInt(), @IsObject()Type check
@IsEmail()Must look like a valid email address
@IsOptional()Field may be omitted entirely
@IsDefined()Field must be present, even if its type is unknown (used for Note.content, see Section 17)
@MinLength() / @MaxLength()String length bounds
@Min()Numeric lower bound (e.g. amounts ≥ 0)
@IsIn([...])Value must be one of a fixed set (e.g. task priority, credential category)
@Matches(regex)Must match a pattern — used to enforce YYYY-MM-DD date strings

Uniform error responses

Where backend/src/common/filters/http-exception.filter.ts
@Catch()
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception, host) {
    const status = exception instanceof HttpException ? exception.getStatus() : 500;
    const message = ... // extracted from the exception, or 'Internal server error'
    response.status(status).json({ statusCode: status, message, path: request.url, timestamp });
  }
}

This is registered globally in main.ts with app.useGlobalFilters(...), so every error — a thrown UnauthorizedException, a validation failure, an unexpected exception — comes back to the frontend in the exact same JSON shape.

How the frontend consumes errors

// src/lib/api-client.ts
async function parseError(res: Response): Promise<never> {
  const body = await res.json();
  const message = Array.isArray(body.message) ? body.message.join(', ') : body.message;
  throw new ApiError(res.status, message);
}

Pages then branch on the status code, e.g. in login/page.tsx: if (error instanceof ApiError && error.status === 401) { ... } to show "Invalid credentials" specifically for a failed login, versus a generic message for anything else.

15.Notifications, Push, and Background Jobs

Three related but distinct concepts

ConceptModuleWhat it is
In-app notificationsNotificationsModulePlain reminder records (title, date, message, read flag) shown in the notification bell / notifications page
Push subscriptionsPushModuleThe Web Push API subscription object a browser gives you when a user allows notifications — stored so the server can later push to that specific browser/device
Background jobsJobsModuleEndpoints meant to be triggered by an external scheduler (cron), which scan the database and actually send push notifications via the web-push library

How a push notification actually gets delivered

How
  1. Browser calls registration.pushManager.subscribe(...) and gets back an endpoint + encryption keys.
  2. Frontend sends that to POST /api/push/subscriptions, stored in the push_subscriptions collection (one document per browser/device, upserted by endpoint).
  3. An external scheduler calls POST /api/jobs/send-reminders or /water-check with the CRON_SECRET.
  4. JobsService queries MongoDB directly (today's notifications, or habits with a water-tracking target), and for each match calls webpush.sendNotification({endpoint, keys}, payload) for every subscription belonging to that user.
  5. If a push fails with HTTP 404/410 (subscription no longer valid — e.g. the user uninstalled/blocked notifications), that subscription document is deleted automatically.

VAPID keys

What VAPID (Voluntary Application Server Identification) keys are a public/private key pair that identifies your server to push services (Chrome, Firefox, etc.) when sending Web Push notifications. 
// backend/src/modules/jobs/jobs.module.ts
private ensureVapid() {
  const publicKey = config.get('VAPID_PUBLIC_KEY');
  const privateKey = config.get('VAPID_PRIVATE_KEY');
  const subject = config.get('VAPID_SUBJECT');
  if (!publicKey || !privateKey || !subject) {
    console.warn('VAPID keys are not fully configured. Push notifications will not be sent.');
    return false;
  }
  webpush.setVapidDetails(subject, publicKey, privateKey);
  return true;
}
Current status VAPID keys are not set in this project's environment (this was true even before the Firebase migration). Every job endpoint still runs successfully and returns {success:true, message:'VAPID keys not configured...'} — it just performs no actual sends. This is a pre-existing gap, not a bug introduced by the migration.

Why the cron logic lives in the backend, not Next.js, now

Before the migration, src/app/api/cron/send-reminders/route.ts and water-check/route.ts used the Firebase Admin SDK to loop over every Firestore user document. Those Next.js API routes were deleted, and the same logic (query → filter → push) was reimplemented in JobsModule against MongoDB — and simplified, since MongoDB lets you query "all notifications dated today across all users" in a single query, instead of looping over every user document and then a per-user sub-collection the way Firestore's nested structure required.

16.Important Security Decisions

DecisionReasoning
Refresh token in an httpOnly cookie, never in a JSON response or localStorageClient-side JavaScript (and therefore XSS) can never read it
Access token kept only in memory, not persistedLimits the exposure window if it were ever exfiltrated; a reload requires a fresh /auth/refresh
Only hashes of refresh tokens and password-reset tokens are stored (SHA-256)A database read/leak alone can't be used to forge a session or reset link — the raw value is required and only ever exists in the one-time email/response
Password-reset tokens are single-use (usedAt) and short-lived (30 minutes, MongoDB TTL index)Shrinks the window an intercepted reset link could be replayed
Resetting a password revokes all of that user's refresh sessionsIf the password was compromised, any existing logged-in session (attacker's or otherwise) is also cut off
Forgot-password always responds {success:true}Prevents using the endpoint to enumerate which emails have accounts
Passwords hashed with bcrypt, cost factor 12Industry-standard slow hash, resistant to brute force even if the database leaks
passwordHash is select: false by defaultPrevents accidental inclusion of the hash in any API response

Global ValidationPipe with forbidNonWhitelisted: trueRejects requests carrying fields the DTO didn't declare, closing off a whole class of injection/override attempts

17.Important Bugs Discovered and Fixed During Migration

These are real issues hit and fixed while building this backend and migrating the frontend to it — not hypothetical examples.

1. Backend wouldn't start — missing dependency

@nestjs/platform-express (the HTTP driver NestJS needs) was not installed. Fixed by installing the version matching the other @nestjs/* packages (v11).

2. Stale incremental build cache masked a missing build

tsconfig.tsbuildinfo persisted after dist/ was deleted, causing TypeScript to believe the output was already up to date and skip re-emitting files entirely. Fixed by deleting the build-info file to force a clean rebuild.

3. Malformed MONGODB_URI

The connection string in .env was, at different points, just a bare password fragment, and later a value with the MONGODB_URI= key itself accidentally missing from the line (a copy/paste artifact) — both silently produced a connection failure rather than an obviously-labelled error.

4. Root tsconfig.json was compiling the backend by accident

The frontend's TypeScript config had no exclude entry for backend/, so running tsc at the repo root tried to type-check the NestJS backend using the frontend's compiler options (no decorator support), producing hundreds of unrelated errors. Fixed by adding "backend" to the root exclude array.

5. Signup appeared to fail, but the account was actually created

use-auth.tsx tried to bootstrap a Firestore profile document for every newly authenticated user — including users authenticated through the new NestJS/JWT flow, who have no Firebase Auth session at all. Firestore's security rules require request.auth != null, so every one of those writes failed with permission-denied, and that thrown error bubbled up and was shown as "Sign-Up Failed" even though the MongoDB user was created successfully. Fixed by removing the Firestore bootstrap from the backend-authenticated code path.

6. Notes could never be created — a missing validator

NoteDto.content had no class-validator decorator at all. Combined with the global ValidationPipe's forbidNonWhitelisted: true, this meant the content field was treated as undeclared and every POST/PATCH /notes was rejected with 400 property content should not exist. Found while migrating the Notes page; fixed with a single @IsDefined() decorator.

7. Destructive "replace-all" semantics on Habits/Planner, discovered the hard way

PATCH /api/habits and PUT /api/planner do not merge — they delete everything and reinsert exactly what was sent. Early testing that sent a partial list silently deleted the rest of a user's habits. Documented and guarded against by always sending the full current array/object from the frontend (see the code comments in habits/page.tsx).

8. Concurrent builds corrupted the shared backend

While multiple parts of the migration were being worked on in parallel, more than one process ran nest build at the same time. Because Nest's build wipes dist/ before regenerating it (deleteOutDir: true), the concurrent wipes and writes corrupted the output and crashed the running server (Cannot find module './modules/auth/auth.module'). Fixed by serializing backend rebuild/restart to a single owner instead of letting it happen from multiple places at once.

9. A stale Firebase session bypassed the new login entirely

Firebase persists its auth session in the browser (IndexedDB) across reloads. A browser that had an old Firebase session (from earlier Guest-mode testing) would auto-restore that session and skip the new backend's login screen — but that session carried no NestJS JWT, so every save silently failed with 401. It looked like "the app just isn't saving anything." Diagnosed by checking which auth path was actually active; resolved by logging out (or clearing site data) to force a real login through the new backend.

10. Resend rejected the email — twice, for two different reasons

First attempt: sending to a @example.com test address was rejected (422) — Resend's sandbox mode only allows sending to the account's own verified address. Second attempt (correct recipient): sending from pranathisundara3@gmail.com was rejected (403 domain not verified) — Resend requires the from domain to be owned and verified, and nobody can verify gmail.com. Fixed by setting MAIL_FROM_ADDRESS back to Resend's sandbox sender, onboarding@resend.dev.

11. PASSWORD_ENCRYPTION_KEY is defined but never implemented

Discovered while migrating the Password Manager feature: despite the field being named encryptedData and an encryption key existing in .env.example, no encryption code exists anywhere in the codebase (confirmed by searching the entire backend source for the variable — it is not referenced). Credential values are stored as plain strings in MongoDB; the UI only masks them visually with dots. This was not introduced by the migration — the same was true of the original Firestore implementation — but it is a real, currently-unaddressed gap (see Section 22).

20.End-to-End Example: Creating a Task

This traces one real user action — adding a to-do item from the Dashboard — through every layer of the system.

Step 1 — User action

On src/app/dashboard/page.tsx, the user types a task into the "Add a new task" dialog and clicks Add Task, which calls addTodo().

Step 2 — Frontend calls the API client

const created = await apiFetch<ApiTask>('/tasks', {
  method: 'POST',
  body: JSON.stringify({ text: newTodoText.trim(), completed: false, priority: newTodoPriority }),
});

Step 3 — api-client.ts builds the real HTTP request

POST http://localhost:3001/api/tasks
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...        (the in-memory access token)
Cookie: refresh_token=... (httpOnly, sent automatically by the browser)

{"text":"Finish Q3 report","completed":false,"priority":"low"}

Step 4 — NestJS receives the request

  1. CORS check (main.ts) — origin must match FRONTEND_URL.
  2. Body/cookie parsing (json(), cookieParser() middleware).
  3. Global ValidationPipe validates the body against TaskDto: text is a non-empty string ≤500 chars (present, OK), completed is a boolean (present, OK), priority is one of high/medium/low (present, OK). If anything failed here, the request would stop right now with 400 Bad Request and never reach the controller.
  4. JwtAuthGuard runs JwtStrategy.validate(): verifies the access token's signature against JWT_SECRET and checks it hasn't expired. If it's expired or invalid → 401 immediately.
  5. TasksController.create() runs, with @CurrentUser() giving it {sub: '6aa...', email: '...'} and @Body() giving it the validated TaskDto instance.

Step 5 — Service writes to MongoDB

create(userId: string, dto: TaskDto) {
  return this.model.create({ ...dto, userId });
}

Mongoose inserts a new document into the tasks collection: {_id: ObjectId(...), userId: ObjectId('6aa...'), text: 'Finish Q3 report', completed: false, priority: 'low', createdAt: ..., updatedAt: ..., __v: 0}.

Step 6 — Response

NestJS serializes the created Mongoose document to JSON and returns it with status 201 Created (Nest's default for a POST handler with no explicit @HttpCode).

Step 7 — Frontend updates the UI

const mapApiTask = (t: ApiTask): TodoItem => ({ id: t._id, text: t.text, completed: t.completed, priority: t.priority });
setTodos([mapApiTask(created), ...todos]);   // new task appears at the top of the list

What happens if the access token had expired at Step 4?

How the retry path works
  1. Backend returns 401 before ever running TasksController.
  2. apiFetch sees res.status === 401 && retry, and calls refreshSession(), which POSTs to /api/auth/refresh (the httpOnly cookie goes along automatically).
  3. AuthService.refresh() verifies the refresh JWT, finds and revokes the matching row in refresh_sessions, and issues a brand-new access+refresh pair (rotation).
  4. apiFetch retries the original POST /tasks request exactly once, now with the new access token, and the flow above continues normally.
  5. If the refresh itself fails (refresh token also expired/revoked), the user is effectively logged out and would need to sign in again.

What deliberately stayed, and why

Nothing Firebase-related remains in the codebase. Two things that might look similar are not Firebase: profile photos are stored as base64 data: URIs directly in MongoDB (no external file storage was introduced), and push notifications use the vendor-neutral Web Push standard (web-push npm package, VAPID keys) rather than Firebase Cloud Messaging.

The overall motivation

  • Full data ownership — all user data lives in a MongoDB database the project controls directly, not a third-party vendor's proprietary database.
  • One consistent backend instead of a split between client-side Firestore access, Firebase security rules, and a handful of server-side Next.js API routes using Firebase Admin.
  • Avoiding the exact class of bugs Firebase's split model caused during this project — e.g. bug #5 in Section 17, where a user could be validly authenticated by the new backend but still get rejected by Firestore's separate security-rule engine, which only trusts Firebase Auth sessions.

22.Important Limitations That Still Exist

Password Manager has no real encryptionCredential values are stored as plain strings in MongoDB (encryptedData: Record<string,string> is just a bag of unencrypted fields). PASSWORD_ENCRYPTION_KEY exists in .env.example but is not implemented anywhere. The UI only visually masks values with dots.
